# Сайт завода «Атланта»

Статический сайт завода: генерируется из каталога CRM, хостится где угодно
(nginx, любой статический хостинг), без CMS и базы данных.

## Сборка

```bash
pip install --break-system-packages pillow   # нужен один раз, для пережатия фото
python3 site/build.py                        # → site/dist
python3 site/build.py --skip-images          # без пережатия фото (быстро)
python3 site/build.py --out /var/www/atlanta # в другую папку
python3 site/build.py --domain https://atlanta.ru   # домен без правки content.json
```

Сборка полностью перезаписывает `site/dist`. В git он не попадает — это артефакт.

## Откуда данные

| Что | Откуда |
| --- | --- |
| Каталог: разделы, позиции, исполнения, характеристики | `server/src/db/catalog/catalog.json` |
| Фотографии | `server/src/db/catalog/files/` |
| Все тексты сайта: главная, преимущества, FAQ, контакты, условия | `site/content.json` |
| Вёрстка | `site/static/css/site.css`, `site/static/js/site.js`, `site/static/img/logo.png` и `logo-mark.png` (знак в шапке) |
| Выкладка | `site/publish.py` — копирование в папку, FTP/FTPS или rsync; тесты — `site/test_publish.py` |

Цены в каталоге (`price = 0`) не публикуются: на сайте везде «цена по запросу».

## Что обновляется автоматически

Правки в `catalog.json` (новые позиции, исполнения, описания, фото) подхватываются
следующей сборкой: карточки, разделы, `sitemap.xml`, `search.json`, счётчики на главной.

Галерея карточки — это фото изделия плюс снимки исполнений (комплектов); повторы
по имени и по содержимому отбрасываются, поэтому снимок фонаря «Л» и «П» из выгрузки
поставщика показывается один раз.

Если позиция стала исполнением другого изделия (`supersedes`), её прежняя страница
остаётся заглушкой с переходом на изделие: старые ссылки и распечатки не ломаются,
а в `sitemap.xml` такие страницы не попадают.

## Что правится руками

- `content.json` → `site.domain` — домен. От него строятся канонические ссылки, Open Graph,
  `sitemap.xml` и `robots.txt`. Поставьте реальный домен перед публикацией.
- `content.json` → `site.requisites` — ИНН/ОГРН для футера (пока пусто — строка не выводится).
- `content.json` → `site.form_endpoint` — URL приёмника заявок. Пока пусто: форма
  открывает письмо в почтовом клиенте (mailto на адрес из первого офиса).
- `content.json` → `contacts` — телефоны, почты, адрес производства.
- Тексты блоков главной, FAQ, сертификаты, условия работы.

## Структура

```
/                                    главная
/catalog/                            все 192 позиции с поиском (в том числе по исполнениям)
/catalog/<раздел>/                   11 разделов
/catalog/<раздел>/<артикул>/         карточки изделий и заглушки прежних артикулов
                                      (у позиций вне печатного каталога source_page = null)
/made-in-russia/                     «Сделано в России»: позиции с записью в ГИСП
/about/ /certificates/ /delivery/ /contacts/ /privacy/ /404.html
/sitemap.xml /robots.txt /search.json
```

## Отметка «Сделано в России»

Раздел `/made-in-russia/` собирается сам: в него попадают позиции, у которых
в каталоге заполнено поле `gisp_url` — ссылка на запись в реестре ГИСП.
Такие позиции получают бейдж «Сделано в России» на фото в каталоге и на карточке
изделия, ссылку «Запись в реестре ГИСП» в блоке документов и
`countryOfOrigin: Россия` в разметке Schema.org.

Ссылку можно завести двумя путями.

**Пачкой, списком.** `server/scripts/catalog/gisp-links.json` — артикул и URL записи.
`match: "prefix"` помечает всё семейство: у жгутов А.3724 одна запись реестра на все
124 артикула и 581 исполнение, у задних фонарей А.3776.001 — на все варианты
`-Б`, `-БЖ`, `.1`, `.1-Б`, `.1-БЖ`. Комплект пишется отдельной строкой: у
`А.3776.005/А.3731.007` та же запись реестра, что у фонаря `А.3776.005`.

```bash
npm run db:apply-gisp              # из списка → catalog.json
npm run db:apply-gisp -- --dry-run # только показать, кого заденет
npm run db:import-gisp             # и в карточки CRM (пустые поля; --force — перезаписать)
python3 site/build.py
```

Скрипт печатает, какие артикулы из списка не нашлись в каталоге, — опечатку видно сразу.

**По одной, из карточки.** Менеджер ставит ссылку в CRM: «Каталог» → карточка позиции →
поле «Ссылка на ГИСП». Дальше её надо перенести в `catalog.json`, из которого собирается сайт:

```bash
npm run db:export-gisp                 # из корня: боевая база (DATABASE_URL)
cd server && npm run demo:export-gisp  # демо-база PGlite
npm run db:export-gisp -- --dry-run    # только показать, что изменится
npm run db:export-gisp -- --prune      # снять отметки, которых уже нет в CRM
python3 site/build.py                  # пересобрать сайт
```

Пустая ссылка в базе значение из `catalog.json` не стирает — иначе одна
незаполненная карточка гасила бы отметку. Чтобы снять отметку, нужен `--prune`
(или удалить `gisp_url` у позиции в `catalog.json` руками).

## Фотографии

Обложка карточки — поле `image`, галерея — массив `images`; если галереи нет,
сайт всё равно покажет обложку. Снимки исполнений лежат в `modifications[].images`
и появляются в таблице исполнений: клик по миниатюре подставляет фото в галерею
изделия. Одинаковые по содержимому снимки (Л и П, 008 и 008.1) показываются один раз.

Фото, загруженные в карточку позиции в CRM, лежат в `server/uploads/images`
и в `catalog.json` сами не попадают. После правок в CRM:

```bash
npm run db:export-images               # из корня: фото из базы → catalog.json
npm run db:export-images -- --dry-run  # только показать, что изменится
npm run db:export-images -- --prune    # галерею привести к тому, что в CRM
python3 site/build.py                  # пересобрать сайт
```

Без `--prune` выгрузка только добавляет снимки: порядок галереи из каталога
сохраняется, а фото, которых в CRM уже нет, остаются. Файлы копируются в
`server/src/db/catalog/files` под именем `<артикул>_<хэш>.<ext>`; повторный
запуск ничего не дублирует.

## Служебные пометки каталога

В описаниях из CRM встречаются внутренние пометки («Потребители: …»,
«Вариантов подключения: N», «На странице каталога несколько вариантов…»).
Их срезает `clean_public()` в `build.py` — на сайт они не попадают.
Если в каталоге появится новая служебная строка, добавьте шаблон в `INTERNAL`.

## Публикация

Сайт живёт на основном домене, CRM — на поддомене `crm.<домен>` (схема и шаги —
в [`docs/deploy-vps.md`](../docs/deploy-vps.md)).

### Выкладка из сборки: `--publish`

Сборка сама копирует готовые файлы в приёмник и **заменяет только изменившиеся** —
обычно это 5–20 файлов вместо всей сборки (сейчас 1071 файл, 35 МБ). Старые файлы
убирает `--prune`, временные недописанные не остаются: каждый файл пишется рядом и
переименовывается.

```bash
python3 site/build.py --publish                        # $SITE_ROOT или /var/www/atlanta
python3 site/build.py --publish /var/www/atlanta       # в папку
python3 site/build.py --publish /var/www/atlanta --prune
python3 site/build.py --publish ftp://user@host/public_html/site
python3 site/build.py --publish root@103.80.87.197:/var/www/atlanta --prune
```

Приёмник определяется по строке: путь на диске (в том числе сетевой или смонтированный
через sshfs), `ftp://`/`ftps://` или `user@host:/путь` (rsync по SSH). Пароль FTP
берётся из `SITE_FTP_PASSWORD` и никогда не пишется в историю команд:

```bash
SITE_FTP_PASSWORD='…' python3 site/build.py --publish ftp://user@host/public_html
```

**Почему FTP-клиенты падают и почему здесь не падает.** FileZilla и панель хостинга
открывают несколько соединений и заливают всё заново при каждом обновлении; на 800+
файлах сервер отваливается. `site/publish.py` работает одним соединением, файлы
сравнивает по содержимому, оборванную загрузку продолжает с того же места
(`REST`), повторяет попытку при обрыве и проверяет размер после каждого файла.
Для капризных серверов есть пауза между файлами: `--pause 0.2`.

Выложить уже собранное, без пересборки:

```bash
python3 site/publish.py --to /var/www/atlanta --prune
python3 site/publish.py --to ftp://user@host/site --dry-run
```

Кэш выложенного лежит в `site/.publish-cache/` (в git не коммитится) — по нему видно,
что уже уехало, чтобы не заливать повторно. `--force` заливает всё заново.

### На сервере

`update.sh` собирает и выкладывает сайт сам, если в `SITE_ROOT` уже лежит наш сайт
(есть `index.html` и `search.json`) или стоит флаг `WITH_SITE=1`:

```bash
cd /opt/atlanta-crm && git pull && sudo WITH_CATALOG=1 ./update.sh
sudo WITH_SITE=1 SITE_ROOT=/var/www/atlanta SITE_DOMAIN=https://atlanta.ru ./update.sh
sudo WITH_SITE=0 ./update.sh            # только CRM, сайт не трогать
```

### Со своей машины

```bash
./scripts/deploy-site.sh root@103.80.87.197 --domain https://atlanta.ru   # rsync
```

nginx-конфиг сайта лежит шаблоном в `deploy/nginx/site.conf` и ставится командой
`sudo DOMAIN=atlanta.ru ./scripts/setup-nginx.sh` (вместе с конфигом CRM).
