## 1. Краткое резюме

«Атланта» — это самодостаточная CRM для производственно-торговой компании (светотехника и комплектующие для прицепов/полуприцепов). Ключевая идея: **агент (ООО «Атланта») продаёт продукцию принципалов, считает комплекты (BOM) по чертежам, применяет наценки по уровням клиентов, получает комиссию и готовит КП/заказы/отчёты.**

Что понравилось:

- Полный сквозной бизнес-цикл: **клиент → чертёж/BOM → расчёт → КП → заказ → отчёт**, а не набор разрозненных CRUD-ов.
- Очень насыщенный и аккуратный UI для «ванильного» JS: темы, витрина/таблица, степперы, таймлайн, карточка клиента с 9 вкладками, PWA.
- Продуманная предметная модель: модификации компонентов с фото, документы/сертификаты с ZIP-выгрузкой, согласование чертежей с версиями и комментариями, уровни цен, НДС, роли.
- Всё работает end-to-end: я поднял систему, загрузил демо-данные и проверил 30+ сценариев API (логин, CRUD, экспорт Excel/PDF, ZIP с кириллицей, комиссии, дашборд, поиск).

Главные проблемы, которые помешают эксплуатации:

| # | Проблема | Влияние |
|---|----------|---------|
| 1 | **Любой анонимный пользователь читает все данные** (при наличии роли `guest`, т.е. после штатного `deploy.sh`/`migrate_roles`: `GET /api/clients/1`, `/api/orders`, `/api/reports/export/excel` → 200 без токена), хотя «гостевой режим» выключен | Утечка персональных данных и коммерческой информации |
| 2 | **Матрица прав не работает на сервере.** Все записи закрыты `adminOnly` — менеджер/технолог получают 403, хотя UI показывает кнопки; одновременно часть write-эндпоинтов (таймлайн, документы, загрузки) открыта любому авторизованному, включая «Наблюдателя» (проверено: 201) | RBAC — фикция; либо блокирует работу, либо не защищает |
| 3 | **Path traversal в документах**: `file_path` из тела запроса попадает в `path.join()` и ZIP-выгрузку. Я выкачал `/etc/passwd` через `POST /api/components/1/documents` + `GET .../download-zip`; `DELETE` пытается удалить этот файл | Чтение/удаление произвольных файлов на сервере (`.env`, дампы, uploads) |
| 4 | **Наценка уровня клиента применяется на клиенте и повторно при каждом редактировании** заказа/КП | Цены «уползают» на 15–30 % за каждое открытие формы |
| 5 | **НДС нигде не фиксируется в документе**, считается «на лету» от текущей настройки; ставка 22 % захардкожена в 4 местах | Пересчёт истории при смене ставки, расхождение с бухгалтерией |
| 6 | **Деплой/эксплуатация**: секреты и пароль БД захардкожены в `docker-compose.yml`, БД проброшена на 5432, нет `.dockerignore` (в образ попадут `.env` и `node_modules`), миграции без учёта применённых, `package-lock.json` в `.gitignore` | Риски безопасности и невоспроизводимые сборки |

Текущее состояние я бы оценил как **крепкий рабочий прототип / внутренняя система для 3–10 пользователей**, которому до продакшена нужны: закрытие доступов, серверный расчёт цен, фиксация финансовых параметров в документах и наведение порядка в миграциях/деплое.

## 5. Модель данных

### 5.1 Группы таблиц и связи

**Клиенты и работа с ними**

```
client_pricing_levels 1──* clients *──1 client_work_statuses
clients 1──* client_contacts        (адресная книга, telegram/MAX)
clients 1──* client_timeline        (call, negotiation, order, payment, …)
clients 1──* client_documents       (файлы, метаданные)
clients 1──* client_drawings        (legacy, данные перенесены в drawings)
clients 1──* drawing_approvals 1──* drawing_approval_versions
                                1──* drawing_approval_comments
```

**Каталог компонентов (BOM)**

```
component_categories 1──* components 1──* component_modifications 1──* component_modification_images
                                    1──* component_documents (certificate | info)
```

**Чертежи/расчёты**

```
drawings 1──* drawing_components *──1 components
                                  *──0..1 component_modifications
          (quantity, item_markup_pct, item_markup_rub)
drawing_clients (drawing_id, client_id, markup_pct, markup_rub, fixed_price)
          — цена для конкретного клиента: фикс-сумма или наценка поверх BOM
drawings.client_id → clients (обязательный владелец; без клиента чертёж не создаётся)
drawings.fixed_price — устаревшее поле, читается только для старых данных
```

**Продажи**

```
principals 1──* orders 1──* order_items (metadata JSONB — состав чертежа)
principals 1──* proposals 1──* proposal_items (is_drawing, drawing_id, image_path)
proposals.order_id → orders (после конвертации)
```

**Оборудование производителей**

```
manufacturers 1──* manufacturer_products *──1 equipment_types
manufacturer_products *──0..1 drawings
manufacturer_products 1──* manufacturer_product_components *──1 components
```

**Система**

```
roles (permissions JSONB) 1──* users
system_settings (key/value JSONB) — НДС
products — legacy, UI не использует
```

### 5.2 Деньги в БД

- Все суммы — `NUMERIC`, `pg` возвращает их **строками** (`"13610.00"`); клиент везде делает `parseFloat` — это работает, но легко забыть.
- `orders`: `subtotal`, `commission_pct`, `commission_amount`, `total`. **В `total` комиссия не добавляется** — считается, что она «заложена в цену» (комментарии в `orders.js:143`, `seed.js`).
- **НДС не хранится ни в одной таблице** — только настройка `system_settings.vat` (`{enabled, rate}`), применяемая при рендере и в PDF.
- Наценки уровней **не хранятся в заказе/КП**: в `order_items.unit_price` уже лежит цена с наценкой, а в `drawing_components` — базовая цена + наценка позиции.
- Валюты нет (всё в ₽, `ru-RU`), ставка НДС по умолчанию 22 %.

### 5.3 Замечания по схеме

1. **Дублирование**: `schema.sql` уже содержит все поля/таблицы, но 16 `migration_*.sql` повторяют то же самое (`migration_sync_v2.sql` — 206 строк копипаста схемы). Нет таблицы `schema_migrations`, порядок применения не фиксируется.
2. `client_drawings` оставлена «для совместимости» (`migration_unify_drawings.sql`), но приложение её не использует — путает.
3. `products` / `order_items.product_id` / `proposal_items.product_id` — фактически legacy: FK сняты, UI кладёт `product_id = components.id` или `NULL`.
4. Нет `updated_at` триггеров, нет аудита изменений (только ручной таймлайн), нет soft-delete.
5. `drawing_components` не имеет `UNIQUE(drawing_id, component_id, modification_id)` — возможны дубли; добавление модификаций использует `NULL` в UNIQUE (в `manufacturer_product_components` из-за этого ограничение не работает).
6. Индексы покрывают только каталог/чертежи. Нет индексов на `orders(status, order_date)`, `orders(client_id)`, `clients(status_id)`, `proposals(client_id)`, `client_timeline(client_id, event_date)` (последний есть в миграции), `order_items(order_id)`.

## 6. Авторизация, роли и доступ

### 6.1 Как задумано

- Пользователь → `users.role` + `users.role_id` → `roles.permissions` (JSONB).
- 8–10 разделов × действия `view/edit/delete/export`.
- Гость (`roles.name='guest'`) — просмотр выбранных разделов без входа.
- UI прячет пункты меню и кнопки через `API.can(section, action)`; сервер должен проверять `hasPermission(section, action)`.

### 6.2 Как работает на самом деле

| Механизм | Фактическое поведение |
|----------|----------------------|
| `optionalAuth` | При отсутствии токена **всегда** создаёт гостя, если роль `guest` существует — даже когда все `view:false` (`auth.js:77-83`). Проверка `if (!perms)` не срабатывает, потому что `{}` — truthy |
| `auth` в роутерах | Пропускает, если `req.user` уже установлен (`auth.js:21-23`), т.е. гостя тоже |
| `hasPermission` | **Ни одного вызова** в проекте — только определение (`role.js:10`) |
| `adminOnly` на write | 68 маршрутов: любая запись = только `role === 'admin'` |
| Write без `adminOnly` | Таймлайн, документы клиента, документы компонента, все `/api/upload/*` — доступны любой авторизованной роли (и создают/удаляют файлы) |
| JWT | `role` + `permissions` внутри токена, TTL 24 ч, отзыва нет; изменение роли применится только после повторного входа |
| `GET /api/roles` | Доступен любому авторизованному — раскрывает матрицу прав |

**Ещё одна ловушка:** в `api.js:52-70` есть резервная логика «если `permissions` нет — считаем по названию роли» (manager/technologist/viewer), но `login` всегда отдаёт `role_permissions || {}`, а `{}` — truthy, поэтому fallback не срабатывает никогда. Если строки роли нет, любой не-админ видит пустой интерфейс.

**Итог:** матрица прав влияет только на видимость кнопок. Серверная модель — «админ или никто», при этом 4 «дыры» обходят и это. Это одновременно и функциональный баг (менеджер не может работать), и security-баг (наблюдатель может писать).

### 6.3 Гостевой режим

- Кнопка «Продолжить без авторизации» появляется, только если хотя бы один раздел гостя включён (`auth.js` route + `auth.js:110-126`).
- Но API при этом **всё равно открыт анонимно** для всех GET-разделов — независимо от матрицы (роль `guest` создаётся `migrate_roles.js`, который запускается в `deploy.sh`). Фактически «гостевой режим» — это только UI-кнопка, а не ограничение.
- Гость получает `id: 0`; записи от гостя в `created_by` не пройдут по FK (но гостю и не разрешены POST). В `client_timeline.created_by = 0` → нарушение FK, если бы разрешили.

## 7. Бизнес-логика

### 7.1 Ценообразование

Три уровня наценок, которые складываются:

1. **Уровень клиента** `client_pricing_levels.markup_pct` (Розница +30 %, Опт +15 %, Крупный опт +5 %, Производство 0 %).
2. **Наценка позиции BOM** `drawing_components.item_markup_pct` / `item_markup_rub`.
3. **Общая наценка расчёта** (поля в калькуляторе, в БД не сохраняются — только в `order_items.metadata`).

Формула расчёта (калькулятор, `calculator.js:717-760`):

```
base      = price × qty                       // price = price_override модификации, если задан
subtotal  = Σ(base + base×item_markup% + item_markup₽)
levelAmt  = subtotal × level_markup%
total     = (subtotal + levelAmt) × (1 + global_markup%) + global_markup₽
```

**Проблемы:**

- Уровень применяется **на клиенте** при сохранении (`orders.js:840-850`, `proposals.js:~700`) — сервер доверяет присланной цене. Прямой вызов API сохранит любую цену.
- При **редактировании** заказа/КП сохранённая `unit_price` (уже с наценкой) снова умножается на `(1 + level%)`. Каждое сохранение — +5…30 %. Это критично для денег.
- Общая наценка калькулятора **не сохраняется в шаблон чертежа** — при повторном открытии шаблона теряется, а в заказе остаётся только в `metadata`.
- `client_pricing_levels` нельзя создать/удалить/переименовать из UI: только `PUT /api/pricing-levels/:id` и только поле `markup_pct` (`pricing-levels.js`).
- Клиент без уровня → наценка 0 и предупреждение в UI, но не блокировка.

### 7.2 Чертежи и калькулятор

**Единая модель (реализована 22.10.2026).** Чертёж — это один BOM (`drawings` + `drawing_components`)
плюс опционально файл. Чертёж может быть привязан к нескольким клиентам через `drawing_clients`;
цена для каждого клиента считается от **его** уровня цен, поэтому один и тот же BOM у «Опла» и
«Розницы» стоит по-разному. Ручная наценка связи (`drawing_clients.markup_pct/markup_rub`)
переопределяет уровень цен для конкретного клиента.

- `client_id` в `drawings` остаётся «владельцем» (кто создал), но видимость определяется связями:
  клиент видит чертежи, где он владелец **или** есть запись в `drawing_clients`.
- Универсальный чертёж = BOM без привязок; в калькуляторе он показывается отдельной группой
  «Универсальные (общий BOM)» и при сохранении привязывается к выбранному клиенту.
- **Архив вместо удаления**: `drawings.archived_at`; `DELETE` переводит в архив,
  `POST /:id/restore` возвращает. Архив скрыт в списках и калькуляторе, но виден по кнопке «📦».
- **Один файл = один чертёж**: `drawings.file_hash` (SHA-256). Повторная загрузка того же файла
  возвращает 409 с существующим чертежом; UI предлагает не копировать, а привязать клиента.
- **Повторное сохранение шаблона обновляет его** (`PUT /api/drawings/:id`), а не создаёт копию.
- **Журнал расчётов**: `drawing_calculations` хранит снимок (BOM-сумма, уровень цен, общая наценка,
  фикс-цена, итог, состав в JSONB, автор, клиент, принципал). Суммы при записи пересчитывает сервер.
  API: `GET/POST /api/drawings/calculations`, `GET /api/clients/:id/documents/calculation-journal`.
- **Связь с заказом**: калькулятор передаёт `drawing_id` в позицию заказа, поэтому заказ связан
  с чертежом (колонка была, но не заполнялась).
- Согласование — **отдельный процесс** (см. 7.8). В калькуляторе чертежи «в согласовании» не участвуют:
  в чертежи попадает только утверждённый файл, и связь фиксируется `drawings.approval_id`
  (уникальный индекс — один чертёж на одно согласование).

Осталось из P2–P3: `prompt()` вместо формы названия (UX-07), inline-`onclick` (UX-12),
экспорт журнала расчётов.

### 7.3 Коммерческие предложения

- Нумерация `КП-0001` от последнего номера (гонка при параллельной работе).
- Позиции: компонент, модификация, чертёж, произвольная строка.
- Наценка уровня применяется при сохранении — та же проблема двойного применения при редактировании.
- PDF — качественный: шапка с реквизитами, таблица, НДС, итоги, подпись; кириллица через Roboto.
- «Перевести в заказ» создаёт заказ, копирует позиции, формирует `metadata` для чертежей, ставит `status='converted'`, `order_id`. Суммы пересчитываются, комиссия — от принципала. Работает.
- В PDF ставка НДС берётся из настроек **на момент печати**; параметр `?vat_rate=` игнорируется, если настройка есть (`proposals.js:350-358`), т.е. UI передаёт его зря.
- Excel-экспорта КП нет (только PDF).

### 7.4 Заказы и комиссия

- Заказ: клиент, принципал, дата, статус (`new → in_progress → paid → completed | cancelled`), позиции, счёт/оплата/трек.
- Комиссия: `commission_amount = subtotal × principals.agent_commission_pct / 100`, `total = subtotal`.
- Номер: `ORD-` + `MAX(id)+1` (`orders.js:116-119`) — при параллельном создании возможна коллизия уникального ключа → 500.
- `PUT /api/orders/:id` **удаляет все позиции и вставляет заново** — меняются id, теряются metadata/is_drawing из старых записей.
- В `PUT` `invoice_path` при отсутствии в теле записывается `NULL` (`orders.js:239`) — редактирование через API без этого поля стирает прикреплённый счёт.
- В `PUT` нет проверки существования принципала → `principalResult.rows[0]` бросит исключение → 500.
- Комиссия считается от `subtotal`, но в отчётах «Итого» = `total` = `subtotal`; дашборд суммирует и отменённые заказы (см. BIZ-06).
- Экспорта заказов (Excel/PDF) нет, хотя README это обещает; экспорт есть только в «Отчётах».

### 7.5 НДС

- Настройка одна на всю систему: `{enabled, rate}`, по умолчанию 22 %.
- `Table.formatMoney()` **везде** добавляет к сумме «(X с НДС)» (`table.js:62-75`) — в том числе к комиссии, наценкам, KPI дашборда. Это методологически неверно и визуально шумно.
- НДС не сохраняется в заказ/КП, поэтому смена ставки задним числом меняет вид старых документов и PDF.
- Ставка 22 % захардкожена в fallback: `settings.js:13`, `table.js:29,36`, `proposals.js:350`.

### 7.6 Отчёты и дашборд

- «Отчёты»: сводка, по клиентам, по принципалам, детализация заказов, Excel (ExcelJS) и PDF (PDFKit), фильтры по периоду/принципалу.
- Дашборд: KPI + графики по месяцам/статусам + последние заказы; второй вид — «Руководитель» (клиенты с суммой/комиссией/последним заказом).
- Названия месяцев в графике — английские (`TO_CHAR(...,'Mon YYYY')`), при ru-RU интерфейсе.
- Отменённые заказы входят в суммы KPI и отчётов.
- `orders-detail` принимает `client_id`, `status` (используется в модалке отчёта), но `by-client`/`by-principal` — нет.

### 7.7 Файлы и документы

- Multer, дисковое хранение `server/uploads/{images,drawings,avatars,documents}`.
- Имена рандомизируются, оригинальное имя декодируется из latin1 — ок.
- Проверка только по расширению; MIME не проверяется; **SVG разрешён** для изображений (потенциальный stored XSS при открытии файла напрямую).
- `/uploads` отдаётся статикой **без авторизации** — любой, кто знает URL, скачает счёт/документ/аватар.
- ZIP-выгрузка использует `doc.file_path` без нормализации — см. SEC-03.
- Удаление файла при `DELETE` документа делает `unlink` по тому же небезопасному пути.

### 7.8 Согласование чертежей

- `drawing_approvals` (waiting/approved/rejected/…) + версии файлов + комментарии.
- UI в карточке клиента: создать, загрузить версию, комментировать, менять статус, «В чертежи».
- **Утверждённый чертёж** переносится в `drawings` через `POST /api/clients/:clientId/approvals/:id/to-drawing`:
  копируется последняя версия файла, создаётся связь с клиентом и `approval_id`. Операция идемпотентна —
  повторный вызов возвращает уже созданный чертёж (`already_exists: true`), в UI кнопка меняется на «Открыть чертёж».
- До статуса `approved` перенос невозможен (400). Согласование может иметь до 10+ итераций (версии файла),
  в калькуляторе участвует только финальный перенесённый чертёж.
- Загруженные версии хранятся как файлы, метаданные — в БД. Нет уведомлений; «кто согласовал» — только `created_by`.

### Волна 1 — «чтобы не потерять данные и не засветить клиентов» — ✅ выполнено

## 12. Вопросы к заказчику (до начала доработок)

1. **Комиссия** — это доход агента (маржинальность) или сумма, которую агент перечисляет принципалу? Должна ли она добавляться к цене клиента?
2. **НДС** — цены в каталоге уже с НДС или без? Нужно ли фиксировать ставку и сумму НДС в каждом заказе/КП и печатать «в т.ч. НДС»?
3. **Наценки** — уровень клиента и наценка позиции должны складываться или уровень применяется к итогу? Округлять до копейки/рубля?
4. **Роли** — кто реально должен создавать/редактировать заказы, КП, чертежи, каталог? Нужны ли ограничения «менеджер видит только своих клиентов»?
5. **Нумерация** — нужны ли префиксы по годам (`ORD-2026-0001`), сквозная или по принципалам?
6. **Отменённые заказы** — исключать из выручки и KPI?
7. **Файлы** — где хранить (диск или S3), нужны ли превью, водяные знаки, срок хранения?
8. **Интеграции** — 1С/банк/ГИСП/Telegram в ближайших планах?
9. **Пользователи** — сколько одновременно, нужны ли мобильные сценарии (калькулятор в поле), офлайн?
10. **Бэкапы/SSL/домен** — кто отвечает, есть ли требования по 152-ФЗ (персональные данные в карточках клиентов)?

## 13. Итог

Проект живой и продуманный: сквозной бизнес-цикл, хорошая предметная модель, качественный для vanilla-JS интерфейс. На момент аудита доступы, расчёт цен и НДС жили на клиенте — это давало и утечки, и финансовые расхождения.

**Раунд P0–P1 закрыт** без переписывания архитектуры: доступ проверяется на сервере по матрице ролей и данным БД, цены и НДС считает `services/pricing.js` и фиксирует в документах, загрузки ограничены `/uploads` и проверкой сигнатур, секреты вынесены в env, миграции получили реестр, клиентский JS экранирует пользовательские данные, появились тесты и CI.

Что осталось до «продакшн-готовности» (P2–P3, см. §9.5): нумерация документов через последовательности, логирование и метрики, лимит тела запроса, бэкапы, аудит изменений, экспорт заказов/КП и связка корзины «Подбора» с документами.
